# INC-1734: Invalid feed XML for titles with ampersands

2024-07-23, 09:10-12:12 UTC, sev3, IC: zi, author: tw

## Summary

feed-builder shipped an escaping refactor that missed one code path for episode titles.

Titles containing `&` were written into generated RSS XML as raw text instead of escaped entities. Podcast directories started rejecting affected feeds as invalid XML. The issue was live for about 3 hours and kept feed updates from propagating for the affected shows until we fixed the serializer and forced a full rebuild.

Alerting was noisy but useful. `FeedBuildLagHigh` fired after rebuilds piled up behind the failed publishes. No other Castlane services were impacted.

## Impact

- about 2,300 feeds were rejected by podcast directories
- impact window was 3 hours and 2 minutes
- affected feeds stopped receiving new episode updates during the incident
- 1,140 shows had at least one episode title with an ampersand in the window
- 17,600 directory fetches returned invalid feed content or were skipped after rejection
- no audio delivery impact
- no data loss, but feed freshness lagged until the rebuild completed

## Root cause

feed-builder had an escaping refactor that moved title formatting into a shared helper. One code path still wrote the helper output directly into the RSS document without XML escaping.

For titles containing `&`, the generated XML became malformed. Podcast directories rejected the feed at fetch time, which blocked ingestion and caused rebuild work to accumulate.

The regression was not caught before deploy because we did not have an automated XML validation step on the feed publish path. We relied on spot checks and rendering tests that covered normal titles, but not invalid characters in live content.

## What went well

- alerting caught the backlog quickly
- support report matched the alert signal, which shortened triage
- rollback was not needed, the fix was small and safe to deploy
- the rebuild path recovered cleanly once the serializer was corrected
- the issue was isolated to feed generation, no downstream data corruption

## What went badly

- the refactor changed escaping behavior without a targeted test for special characters
- we did not validate the final RSS document before upload
- directory rejection was only visible after publication, so the blast radius was larger than it should have been
- the incident took too long to confirm because initial checks focused on job health, not XML correctness
