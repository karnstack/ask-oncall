# INC-1781: Origin overload after a cdn-edge cache key change

2024-10-08, 14:10 UTC to 15:00 UTC, sev2, IC: yu, author: bo

## Summary

At 14:10 UTC we rolled out a `cdn-edge` config change that added the full query string to the audio cache key. That change was meant to improve cache correctness for a small set of audio URLs that use query parameters. In practice, app-added tracking parameters were present on most requests, so the cache key became effectively unique per request.

That dropped the audio cache hit ratio from about 97 percent to 58 percent within minutes. Traffic that should have been served from edge started going to origin instead. The sudden increase in origin fetches pushed object storage into throttling, which in turn made audio requests slow to start. The user-visible issue lasted about 50 minutes until we reverted the cache key change and the cache hit ratio recovered.

`feed-builder` was not the source of the problem, but it was affected indirectly because more feed page loads were followed by slower audio starts, which increased support noise and made the incident broader than a pure edge event. We also saw a `TargetDown` alert for one of the edge targets during the worst part of the saturation, but it was a symptom of the overload, not a separate failure.

## Impact

- Audio start latency increased across production traffic for about 50 minutes.
- The cache hit ratio for audio fell from 97 percent to 58 percent.
- Origin fetch volume increased by roughly 2.4x compared to the 15 minute baseline before the change.
- Object storage returned throttling responses on a sustained basis during the peak.
- About 31 percent of audio requests saw start times above 2 seconds, where normal was under 300 ms.
- Roughly 18 percent of requests retried at least once before playback began.
- We estimate around 64,000 listener requests were affected during the window.
- No data loss occurred and no feed content was corrupted.

## Root cause

The root cause was a cache key change in `cdn-edge` that included the complete query string for audio objects. That was intended to reduce the chance of serving the wrong variant when query parameters are meaningful.

The problem was that our audio URLs carry tracking parameters added by the client apps and by some referral links. Those parameters are not part of the content identity. Once they were included in the cache key, almost every request became a distinct cache entry. In other words, the cache stopped being shared across listeners for the same file.

This changed the traffic shape in a bad way:

1. Edge cache miss rate increased sharply.
2. Origin traffic jumped to object storage.
3. Object storage began throttling the burst.
4. Slow origin responses made playback startup slow.

We did not have a guardrail to detect a sudden cache hit ratio collapse after a config rollout. We also did not have a canary specifically watching audio object hit ratio by key shape, so the issue was only obvious after the user-facing latency impact had already started.

## What went well

- The change was rolled out cleanly, which made the rollback path simple.
- Grafana made the hit ratio drop obvious once we looked at the right dashboard.
- The oncall response was fast, and we identified the faulty key change within 17 minutes.
- The rollback restored service without needing any emergency code changes.
- We had enough signal from origin traffic, cache hit ratio, and object storage throttling to confirm the mechanism quickly.

## What went badly

- We treated a cache key expansion as a low-risk config tweak, when it directly changed request deduplication behavior.
- We did not strip non-content query parameters before building the audio cache key.
- There was no preflight check for cache key cardinality or a threshold alert on cache hit ratio drop.
- The rollout reached production before we had tested with realistic tracking parameters in the request sample set.
- The blast radius was larger than expected because the new key behavior applied to all audio traffic, not just the small subset we intended to isolate.
