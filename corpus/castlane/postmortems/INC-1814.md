# INC-1814: Quiet episodes from a loudness normalisation bug

2024-12-03, 2024-12-01 09:10 UTC to 2024-12-03 13:40 UTC, sev3, IC: @lm, author: @pk

## Summary

A transcoder release changed the loudness normalisation target from `-16 LUFS` to `-26 LUFS`. New uploads and queued re-transcodes from that window produced audio that was about 10 dB quieter than expected. The issue lasted just over two days and was not caught by alerts.

We found it through creator support tickets, where listeners reported that recent episodes sounded much quieter than older catalog episodes and other shows. The transcoder rollout itself completed cleanly, and the first signal was a cluster of ticket descriptions rather than any operational alert.

The bad output was confined to media generated by `transcoder` during the affected release window. Once we confirmed the regression, we rolled back the release, restarted the queue workers, and re-transcoded affected episodes.

## Impact

- 3,400 episodes were re-transcoded after the fix.
- 1,980 distinct shows had at least one affected episode.
- 214 creator support tickets were linked to the issue.
- 68 creators reported listener complaints about volume mismatch.
- 2 days, 4 hours, 30 minutes of output was generated with the wrong loudness target.
- No data loss, no feed outage, and no CDN issue.
- The issue affected both newly uploaded episodes and queued backfills, but only for audio processed by the bad `transcoder` build.

The user impact was limited to playback quality, but it was broad enough to create visible support load and creator concern.

## Root cause

A release in `transcoder` changed the default loudness target constant from `-16` to `-26`. The code path was used by the normalisation stage for all episode output, including re-transcodes. The mistake was introduced in a refactor where a config value was renamed and a fallback literal was updated incorrectly.

The relevant change was small and looked harmless in review, which made it easy to miss:

```diff
- const TARGET_LUFS = -16;
+ const TARGET_LUFS = -26;
```

There was no corresponding integration test that measured the actual loudness of generated output. We had tests for job completion and file creation, but nothing that validated the audio characteristics of the produced file. Because the queue drained successfully, no infrastructure signal surfaced.

The absence of monitoring made the detection path entirely manual. Support tickets arrived before any engineer looked at the audio samples, and our dashboards only showed normal transcode throughput.

## What went well

- Support ticket triage was fast once the pattern was recognised.
- The release was easy to identify because the `transcoder` deployment history was clean and narrow.
- Rollback was low risk and immediate.
- `ffmpeg` made reproduction straightforward, which shortened the diagnosis loop.
- Re-transcoding was operationally simple once the correct version was back in place.

## What went badly

- We shipped a loudness regression without a guardrail on output quality.
- Review focused on job flow and queue health, not the actual audio parameter change.
- We had no automated sample check for LUFS target drift.
- The issue was silent from an infrastructure point of view, so normal alerting did not help.
- Creator support had to absorb the first wave of detection, which was avoidable.
