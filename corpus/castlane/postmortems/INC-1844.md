# INC-1844: Uploads over 1 GiB failed after an ingress chart upgrade

2025-01-21, 09:10 UTC to 14:05 UTC, sev2, IC: lm, author: lm

## Summary

At 09:10 UTC, uploads larger than 1 GiB started failing in `upload-api` with HTTP 413 responses after we rolled out an ingress chart upgrade in `prod-us-east`. The upgrade reset the ingress body size annotation back to the chart default, so requests above the default limit were rejected before they reached the application.

This lasted for about 5 hours. Small uploads continued to work, so the problem only showed up for creators uploading long-form episodes, which tend to be the largest files we accept. The first clear signal came from support reports and a spike in upload failures, not from an internal alert. We did not have a synthetic check covering large file uploads at the time, so the regression was only visible once real customer traffic hit it.

The fix was to restore the expected request body size setting on the ingress and verify that large uploads succeeded again. We then added a synthetic upload check for a file over 1 GiB so this specific regression should be caught earlier next time.

## Impact

- Uploads over 1 GiB failed for 5 hours and 55 minutes.
- Roughly 3,200 upload attempts were affected.
- About 410 unique creators saw failures.
- Around 180 long-form episodes were delayed, mostly in the 60 to 180 minute range.
- The failure rate for upload requests above 1 GiB peaked at 100 percent, while smaller uploads stayed near baseline.
- Support saw a burst of creator reports, and the public symptom was a repeated error like:
  - `HTTP 413 Request Entity Too Large`
  - `upstream sent too large response`
- No data was lost. Existing uploads that completed before the regression were not affected.
- Transcoding and feed building were downstream of the failed uploads, so those shows simply waited on a successful re-upload.

## Root cause

The ingress chart upgrade changed how the request body limit annotation was rendered. Our ingress had previously been configured to allow uploads above 1 GiB for `upload-api`. During the upgrade, that annotation was no longer set in the generated manifest, so the ingress controller fell back to its default request body limit.

That default is below our supported large-file upload size, which is why only uploads above 1 GiB failed. The application itself was not rejecting the files. The failure happened earlier in the request path, so `upload-api` never received the body.

A representative error from the client side was:

```text
HTTP 413 Request Entity Too Large
```

And on the ingress side we saw entries consistent with body rejection before proxying to the service.

We missed this because the chart change was reviewed as a routine upgrade, and we did not have a synthetic test that posts a file larger than 1 GiB through the full upload path. We had only smaller synthetic checks, which would not have caught a limit regression at the ingress layer.

## What went well

- The problem was isolated quickly to the ingress layer, not the application or storage path.
- Small uploads kept working, so creators could still upload short episodes while we investigated.
- The rollback path was simple, restore the body size annotation and reload ingress.
- Verification was straightforward once we knew the failure mode, a single large test upload proved the fix.
- Support got enough detail to tell creators it was a request size issue and not a problem with their audio files.

## What went badly

- The ingress upgrade removed a critical behavior change without a specific review checklist for upload limits.
- We did not have a synthetic check for a large upload path, so there was no early automated warning.
- The incident started during normal business hours, but we still spent time confirming that the problem was not in `upload-api`, transcoding, or object storage.
- We had to rely on user reports for initial detection instead of alerting.
