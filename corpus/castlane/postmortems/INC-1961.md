# INC-1961: Download counts doubled for six hours
2025-08-05, 08:10 UTC to 14:10 UTC, sev3, IC: zi, author: zi

## Summary

At 08:10 UTC we deployed a change to `download-stats` that was meant to reduce duplicate counting for the same listener and make the dedup logic more consistent across request paths. The change was incomplete. On one path, the dedup window key was changed from `IP + user agent` to `IP only`, while on another path we still counted a download before deduplication ran. That meant some requests were accepted twice, and some were deduped using a broader key than intended. The net effect was that creators saw download counts roughly double for six hours.

We first noticed the issue through creator reports and then confirmed it in Grafana by comparing the live counters with the raw event rate. Once we understood the shape of the bug, we stopped the bad deployment, recomputed the affected counts, and backfilled the corrected totals.

This was a sev3 because it affected reporting accuracy rather than audio delivery or feed availability, but it directly impacted creator trust and payout-adjacent analytics. We should have caught this in staging, and we should have been more careful about changing dedup behavior in two separate code paths at once.

## Impact

The issue lasted from 08:10 UTC until 14:10 UTC.

- Affected service: `download-stats`
- Affected surface: creator download counts in dashboards and internal reports
- Estimated impacted shows: about 4,800 active shows
- Estimated impacted downloads: about 3.1 million downloads were double-counted during the window
- Worst-case inflation on individual shows: 1.9x to 2.2x depending on traffic mix
- Creator-facing reports were wrong for six hours until recompute finished

There was no data loss. The raw event log was intact, and we were able to recompute the correct totals after we isolated the bad interval.

## Root cause

The root cause was a deploy that changed the dedup window key on only one of the two download counting paths.

Historically, `download-stats` handled two related flows. One path ingested edge events and deduped them by a short window keyed on `IP + user agent`. Another path handled a fallback stream and applied dedup later in the pipeline. The intent of the deploy was to simplify the keying strategy so both paths would behave the same way. During implementation, one code path was updated to use `IP` only, but the other path still performed the count before dedup ran.

That created two problems at once. First, `IP` alone was too broad, so unrelated listeners behind shared networks could collapse into one bucket and trigger odd retry behavior in our counters. Second, because the fallback path counted before deduplication, a request could be recorded once on the early path and once again after dedup logic ran. Together, those mistakes inflated counts rather than canceling out.

We missed this in review because the diff looked like a small cleanup and the tests only covered a single request path. We also did not have a staging check that compared the live aggregate against the raw event rate for this specific code path. The existing alerting did not fire because the system was still processing requests successfully, just counting them incorrectly.

## What went well

- We got a creator report quickly, which shortened the time to detection.
- The Grafana panels for live counts versus raw events made the mismatch obvious once we looked.
- The raw event data was complete, so recompute was possible without manual reconstruction.
- The rollback was low risk and stopped the inflation before the next full traffic cycle.
- We were able to explain the issue clearly to support and avoid speculation.

## What went badly

- We changed dedup behavior in two places, but only validated one.
- The review did not force us to reason through both request paths together.
- We did not have a staging assertion that would have caught double counting within minutes.
- The deploy went out during normal traffic without an automatic canary check on count drift.
- Our internal dashboards showed the symptom, but we had no direct alert for logical overcounting.
