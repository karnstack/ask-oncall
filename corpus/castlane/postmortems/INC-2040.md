# INC-2040: Rounding error in one currency

2025-12-15, 06:00 to 18:20 UTC, sev3, IC: nd, author: cv

## Summary

During the December creator batch, 2,100 payouts in one currency were underfunded by 0.01 each in the payout calculation path. The issue was caused by rounding per line item before summing, instead of rounding the batch total and then allocating cents across rows. The result was a batch total that was 21.00 below the ledger-derived amount for that currency.

The error was not user-visible in the sense of failed payout creation, but it did create a reconciliation mismatch between the payouts system and the ledger. The ledger reconcile job caught the discrepancy within the same day. We paused further batch completion for the affected currency, validated the delta, and sent top-up payouts the next day to make every creator whole to the cent.

This was a sev3 because no payouts were lost and the mismatch was contained to one currency in one monthly batch, but it required manual intervention and delayed final reconciliation.

## Impact

- 2,100 payouts in one currency were each short by 0.01.
- Total shortfall for the currency was 21.00.
- 1 monthly batch file was generated with an incorrect currency total.
- 1 ledger reconciliation alert fired internally through our scheduled reconcile check.
- 2 payout operators and 1 engineer were involved in investigation and remediation.
- 0 creators were permanently underpaid after the top-up payouts were sent on 2025-12-16.
- 0 other currencies were affected.

## Root cause

The payout calculation code for one currency used a per-line rounding step on each creator share before summing the batch. In this currency, that produced a systematic 0.01 shortfall for each of the 2,100 payouts in the batch.

The intended behavior is to compute the batch total at full precision, round only at the currency boundary, and distribute any residual cents using the deterministic allocation logic already used elsewhere in payouts. That path was not followed in this code path after a recent change to improve readability in the batch formatter. The change preserved the per-payout display values, but it altered where the final rounding happened.

Because the ledger reconcile job compares final expected batch totals rather than individual display lines, it caught the mismatch immediately after batch generation. This limited the blast radius to a single day and prevented a long-lived discrepancy.

## What went well

- Ledger reconcile caught the mismatch before the batch was considered complete.
- The discrepancy was limited to one currency, not the full December batch.
- We had a clear deterministic reproduction path in staging.
- The payout records were internally consistent, which made it straightforward to compute the exact top-up amount.
- Top-up payouts were issued the next day without needing any manual data repair.
- Communication in #oncall-payouts stayed focused on the exact currency total, which reduced confusion.

## What went badly

- The code review did not flag the change in rounding placement.
- We lacked an automated test that asserts the batch total equals the sum of final ledger rows for currencies with fractional cent distributions.
- The batch job surfaced the problem only after generation, so we spent time confirming the exact delta before remediation.
- The operational playbook for this case did not include a prewritten top-up path, so the first response included some manual calculation and validation.
