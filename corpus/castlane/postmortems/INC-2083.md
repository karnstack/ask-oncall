# INC-2083: Staging audio bucket listable from the internet

2026-02-24, 2026-02-21 09:00 UTC to 2026-02-24 11:20 UTC, sev3, IC: sec-ir, author: sec-ir

## Summary

A staging object storage bucket that held test audio was publicly listable for approximately 3 days. The exposure started after a Terraform module change landed in the platform infrastructure repo and was applied to the staging environment. The change unintentionally removed the access control setting that prevented anonymous list access on the bucket.

The issue was detected by our weekly external security scan on 2026-02-24 at 11:20 UTC. No personal data was present in the bucket. The contents were limited to synthetic test audio, temporary build artifacts, and a small number of internal staging files used by media workflows. We treated this as a security incident because the bucket metadata and object names were exposed to the internet.

The bucket was remediated by restoring the previous access control setting and reapplying the Terraform state. We also reviewed the module change, tightened the policy check in CI, and verified that no other staging buckets inherited the same configuration path.

## Impact

- Public exposure window: 3 days, 2 hours, 20 minutes.
- Affected bucket count: 1 staging bucket.

## Root cause

The root cause was a Terraform module change in the platform infrastructure code that changed the default bucket policy behavior for a staging object storage resource. The module was intended to simplify bucket provisioning, but the specific input used by the staging stack no longer preserved the explicit "deny public listing" setting.

The CI policy check did run, but it only checked for a narrow set of public-read configurations. It did not assert that list access remained blocked when the module rendered the final bucket policy. As a result, the change passed review and applied cleanly even though it created public listability.

This was a configuration management failure, not a runtime failure. The bucket contents were staging-only, and no service code was involved.

## What went well

- The weekly external scan caught the issue quickly after it was introduced.
- The alert path reached security and platform within minutes.
- The incident was scoped rapidly, and we confirmed that no personal data was present.
- The remediation was straightforward, a Terraform revert and reapply restored the intended state.
- Post-remediation validation was clear and repeatable.

## What went badly

- The module change altered a security-sensitive default without enough guardrails.
- The CI policy check was too narrow and did not verify the final access posture.
- There was no separate drift check for staging buckets that would have caught the public listing before the weekly scan.
- The change affected a staging asset, but the review process treated it as low risk because the bucket contained test data.
- We relied on one control, the scan, to catch a class of misconfiguration that should have been prevented earlier.
