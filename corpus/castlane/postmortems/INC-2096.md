# INC-2096: ad-stitcher timeouts slowed episode starts
2026-03-17, 14:10 UTC to 15:02 UTC, sev3, IC: yu, author: pk

## Summary

At 14:10 UTC we started seeing longer episode start times for a subset of ad-supported shows in prod-us-east. The issue was in `ad-stitcher`, where the ad decision cache was effectively disabled by a config typo. Every request for an ad-supported episode waited on the ad decision call instead of hitting cache, and the fallback timeout was still too high at 1.5 s. That added about 2 s to first play for affected requests.

`cdn-edge` traffic was healthy, but it amplified the symptom because the player retry path re-requested manifests and segments while the start request was still blocked upstream.

The immediate fix was to correct the config, restore the cache, and lower the fallback timeout so bad decision calls would fail open faster.

```bash
kubectl -n edge get deploy ad-stitcher -o jsonpath='{.spec.template.spec.containers[0].env}' | jq
flagctl get ads.stitching_enabled
```

## Impact

This was limited to shows with ads enabled in prod-us-east.

- 18.4% of episode starts for ad-supported shows were delayed.
- 41,263 start requests were affected during the incident window.
- p95 time to first audio rose from 1.3 s to 3.2 s for impacted requests.
- p99 time to first audio rose from 2.1 s to 5.4 s.
- 312 unique shows saw at least one delayed start.
- No data loss, no billing impact, and no persistent user-facing corruption.

Users mostly saw longer loading spinners before playback began. Some retried, which increased load on `ad-stitcher` and caused a small spike in `cdn-edge` 5xx responses on a few nodes, but those recovered after the cache was restored.

## Root cause

The root cause was a configuration typo in the `ad-stitcher` deployment that disabled the ad decision cache. The intended setting was to keep a small in-memory cache enabled for repeated requests from the same show and episode combination. The deployed value was parsed as false due to a malformed string in the config map.

With the cache disabled, every request went to the ad decision service synchronously. When that service was slow or briefly unavailable, `ad-stitcher` waited up to 1.5 s before falling back. That was acceptable when the cache was working because only a small fraction of requests hit the upstream path. With the cache off, the wait happened on every request, and the added delay stacked with normal playback startup.

The config typo was introduced during a routine rollout and was not caught because the deployment only checked that the pod started, not that the effective runtime value matched the intended setting.

## What went well

- `cdn-edge` stayed up and did not need any rollback.
- The incident was visible quickly through latency metrics, not just user reports.
- The oncall path to confirm the issue was short, and the deployment was easy to compare against the previous revision.
- The config fix was low risk, and the recovery was fast once the bad value was identified.

```bash
flagctl get ads.show.12345
kubectl -n edge rollout status deploy/ad-stitcher
```

## What went badly

- The config typo disabled a performance-critical cache without failing the deployment.
- We relied on a fallback timeout that was too generous for the no-cache path.
- The config review did not include a check of the effective rendered value, only the template diff.
- We did not have a dedicated alert for ad-start latency, so the issue surfaced as elevated player latency rather than a direct service signal.
