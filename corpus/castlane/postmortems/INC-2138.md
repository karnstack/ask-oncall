# INC-2138: upload-api crash loop after a Secret key rename

2026-05-26, 14:10 to 14:34 UTC, sev3, IC: @lm, author: @lm

## Summary

At 14:10 UTC, a rollout of `upload-api` in `prod-us-east` started failing because a Secret key name had been changed in one place, but not everywhere. The new pods came up, read the Secret, and then exited during startup because the expected environment variable was missing. Kubernetes kept the old pods serving traffic while the rollout was in progress, so we did not lose the service entirely. We did have reduced capacity for about 20 minutes until the rollout progress deadline was hit and the bad rollout was rolled back.

This incident only affected `upload-api`. The symptom was a `KubePodCrashLooping` alert on the new ReplicaSet. Upload requests continued to succeed, but the service had less headroom than usual while the new pods were not becoming Ready.

## Impact

- Duration of reduced capacity: 20 minutes, from 14:14 UTC to 14:34 UTC
- User-facing upload failures: 0
- Failed transcode jobs: 0
- Failed uploads recorded in application logs: 0
- New `upload-api` pods repeatedly restarting: 3 pods across the rollout
- Peak error rate on the service: no sustained increase, but readiness stayed below target for the new ReplicaSet
- Customer impact: some requests saw slower queueing under load, but no uploads were dropped or rejected

We treated this as sev3 because the service stayed up and customer data was not lost, but the rollout was blocked and capacity was reduced during a busy period.

## Root cause

A Secret key was renamed from `upload_signing_key` to `UPLOAD_SIGNING_KEY` in the Secret object, but the `upload-api` Deployment still referenced the old key name through `valueFrom.secretKeyRef`. The new pods were created with an empty value for the required configuration, and the application treats that as fatal on startup.

The important detail is that this only broke the new pods. The old ReplicaSet kept running with the previously resolved environment, so traffic continued to be served while the rollout was in progress. Because the rollout strategy allowed old pods to stay up until the new ones were Ready, the issue manifested as reduced capacity rather than a complete outage.

This was a configuration drift problem, not an application code bug. The rename was made in one place during a Secret cleanup, but there was no matching update in the Deployment manifest, and the change was not caught in review.

## What went well

- `KubePodCrashLooping` fired quickly, which made the failure easy to spot.
- The old pods stayed in service, so there was no customer-visible outage and no failed uploads.
- Pod logs were clear, and the startup failure pointed directly at the missing configuration.
- The team checked actual upload success before taking action, which avoided unnecessary disruption.
- Rollback was simple and safe because the prior manifest was still valid.

## What went badly

- The Secret rename was only updated in one place, so the change was inconsistent across the stack.
- We did not have a validation step that checked that every `secretKeyRef` still matched current Secret keys.
- The rollout allowed the bad ReplicaSet to churn for longer than it needed to before rollback.
- The review process for the Secret change did not include a check against the deployment manifests that consume it.
- We noticed the crash loop through the alert, but not through a pre-deploy check, which would have been better.
