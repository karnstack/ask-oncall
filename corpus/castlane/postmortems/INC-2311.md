# INC-2311: Episode takedowns delayed by the purge rate limit

2026-11-02, 14:10 UTC to 15:02 UTC, sev3, IC: @yu, author: @bo

## Summary

A creator removed 1,400 episodes in one action, and the takedown path in `cdn-edge` tried to purge each audio URL individually. The purge API enforced a 300 requests per minute rate limit, so the invalidation queue backed up immediately. Most URLs were purged in the first few minutes, but the tail of the batch stayed in cache for up to 25 minutes.

This was an edge caching problem, not an origin serving problem. The audio objects themselves were already gone from storage, but cached copies continued to serve until their TTL expired or the URL purge finally landed. We should have used surrogate key purges for the bulk removal path, and only fallen back to per-URL purges for small changes.

## Impact

- 1 creator bulk removal affected.
- 1,400 episode URLs scheduled for purge.
- 1,107 URLs were invalidated within 6 minutes.
- 293 URLs remained cached past the intended takedown window.
- Worst case stale audio was served for 25 minutes after the removal request.
- Estimated stale plays: 418 requests across podcast apps and directories, based on CDN logs.
- No data corruption, no auth issue, and no cross-tenant exposure.
- Severity was sev3 because the issue was limited in scope, but it directly affected content removal correctness.

## Root cause

The takedown workflow in `cdn-edge` used the same code path for both small removals and bulk removals. For each episode, it issued a separate URL purge request. That works fine for a handful of URLs, but it does not scale when a creator removes thousands of episodes at once.

The purge service rate limit is 300 requests per minute. At 1,400 URLs, the queue needed almost five minutes just to get through the request volume, and that assumes no retries and no other purge traffic. In practice, the worker had retry backoff and a few transient failures, so the tail stretched out to 25 minutes.

We already tag episode responses with surrogate keys, which means a bulk takedown can be handled with a small number of key purges instead of thousands of URL purges. The problem was that the bulk-removal branch did not exist in the production takedown path. The edge cache hit ratio was healthy, but in this case that was the wrong optimisation, because we needed faster invalidation rather than better cache retention.

## What went well

- The removal request was isolated to one creator, so blast radius stayed small.
- We had clear CDN logs that let us measure stale serves and confirm the issue was cache related.
- The audio objects were already deleted upstream, so there was no risk of new origin fetches recreating the stale content.
- The team moved quickly to surrogate key purges once the pattern was understood.
- Existing TTLs limited the maximum stale window, so the issue self-healed without a manual cache flush.

## What went badly

- The takedown path assumed URL purges were good enough for all batch sizes.
- We did not have a hard guardrail or branching logic for bulk removals.
- The rate limit was known, but we had not translated that into an operational threshold in the workflow.
- There was no alert that specifically described purge backlog growth, so detection depended on logs and a user report.
- The code path made cache invalidation look successful before the queue actually drained, which hid the real latency from the requester.
